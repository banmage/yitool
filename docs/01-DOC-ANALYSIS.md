# 文档分析与一致性审查

**审查对象：** `docs/` 下五份规范
**审查日期：** 2026-11-03
**审查方法：** 逐文档阅读 + 跨文档条款比对 + 关键示例复算（使用 `sxtwl` 与 `lunardate` 交叉核验公农历/干支）
**结论：** 文档体系完整、职责边界清晰，可作为阶段 0 的输入；但存在 **9 项阻塞级（P0）不一致**，必须在冻结前修正，否则会直接污染种子、金标准、数据表与历史复现。

---

## 1. 文档体系与依赖

```text
SRS v0.4  行为、边界、功能、验收
 ├── ARS v0.2  梅花 / 焦氏 / 纳甲 / 择吉算法、映射、金标准
 ├── IR  v0.1  计算结果 → 文字解释、措辞等级、合规
 ├── CAL v0.1  公农历、节气、干支、日界、时区、旬空
 └── TDS v0.1  架构、接口、存储、技术栈、部署
```

强制约束（五份文档一致）：

1. ARS 不实现历法，只调用 CAL。
2. IR 不重算卦象，只消费 ARS 结构化结果。
3. TDS 不重定义算法/解释/历法，只定义实现。
4. 任何规则必须带 `rule_id`、层级、来源、版本、测试样例。
5. 未冻结项必须标注“待校核”，不得发布正式结果。

## 2. 逐文档分析

### 2.1 SRS v0.4

**优点**

- 合规定位、使用边界、不做事项写得很清楚，可直接作为产品边界。
- 九色/传统数字双输入、种子链拆分、隐私复现边界、A/B 两种模式、纳甲完整化、历法双表分离、择吉三层模型、IR 独立、版本 ID 统一、阶段与优先级对应，均已成体系。
- FR-01～FR-12 与 NFR 覆盖了阶段 1–5 的主要能力，验收标准多数可测试。
- 附录 B 日志 Schema、附录 C 免责声明、附录 D 引用关系可直接落地。

**缺口**

1. **文档状态表过期**：1.3 仍写 ARS“待修订冻结”、IR/CAL“待新增”、TDS“暂缓”，但四份文档均已存在。
2. **缺少“忌神五行/弱势卦位”的算法出处**：3.2.1、3.7、4.6 要求梅花输出忌神与弱势卦位，但 ARS 第 3 章只定义起卦、互变、体用、旺衰，没有忌神/弱势卦位的计算规则。IR 3.4 已假设该输入存在。
3. **数据字典与 ARS 不一致**：附录 A 与 ARS 附录 D 的表清单、状态、版本号不一致（见 A-05）。
4. **种子字段不完整**：3.3.2 基础种子字段缺少 ARS 2.2 已加入的 `timezone`、`day_bound`。
5. **日志版本字段不完整**：附录 B 只列 `ir`，未列 IR 的 `ir_rule_set`、`ir_template_set`（IR 10.1 要求）。
6. **性能指标缺少统一测试矩阵**：6.2 给了目标，但未规定统一的样本量、数据库规模、是否含缓存/初始化；CAL 9.1 与 TDS 10.3 各自表述。

### 2.2 ARS v0.2

**优点**

- 九色/传统数字双模式公式明确，且有可复算的金标准（TC-MEIHUA-001/002）。
- 种子链已消除循环依赖，A/B 有独立公式。
- 纳甲装卦流程 12 步完整，给出乾/坤金标准与多卦测试要求。
- 择吉统一规则抽象 `ZEJI-RULE-01`，避免每种规则硬编码。
- 附录 A 六十四卦八宫表、附录 B 纳甲干支表可直接转数据文件。
- 待冻结项 F-01～F-12 清晰。

**缺口**

1. **忌神/弱势卦位算法缺失**（与 SRS 3.2.1/3.7 对应），IR 无法落地。
2. **`bazi_material_hash` 未定义**：3.2 的 `B_mod` 依赖该值，但全文没有定义其来源、规范化方式、是否加盐。
3. **`question_hmac = "NONE"` 时 Q_mod 行为未定义**：`int("NONE",16)` 会报错；且“是否保存问事关联”会改变 Q_mod，进而改变固定模式结果，破坏可复现语义。
4. **A/B 固定派生随机语义冲突**：2.5 的 `A_run_seed/B_run_seed` 含各自 `question_hmac` 与 `AB_A/AB_B` 标签；而 2.8 的 `FIXED_DERIVED` 六爻由 `sub_seed(run_seed)` 派生。结果是“统一条件对照”在固定模式下仍可能得到不同六爻（见 A-03）。
5. **变卦六亲流派未裁决**：5.6 要求变卦“独立宫五行、独立六亲”，但传统六爻常见做法是变卦六亲随本卦宫五行；这是影响金标准的实质分歧，需易学评审确认。
6. **W-02 与 ZEJI-RULE-01 关系不清**：SRS 3.4 讲权重表 W-02，ARS 1.11 用 ZEJI-RULE-01 的 `weight` 字段；两者是同一表还是两层表未说明。
7. **互卦乾坤特殊规则描述模糊**：“启用时按变卦取互”未给公式。
8. **日界/时区未进入梅花日志示例**：8.1 日志 Schema 未单列 `timezone/day_bound`，虽然 2.2 种子已含。

### 2.3 IR v0.1

**优点**

- 输入/输出对象、措辞等级、各引擎模板、冲突解释、合规扫描、版本迁移完整。
- 明确“不重算、不合成、不绝对断语”，与 SRS 合规要求一致。
- 冲突来源五分类（规则体系/输入/随机快照/数据待校核/模板差异）可直接实现。
- TC-IR-001～006 覆盖匹配、禁用词、冲突、信息不足、旧版本、声明。

**缺口**

1. **等级判定存在二选一未定**：3.1 体克用为 `FAVORABLE/NEUTRAL`，5.1 用神空亡为 `CAUTIOUS/OBSERVE`，需要确定性选择规则。
2. **等级调整边界未定义**：3.2 “上调/下调一级”在最高/最低等级时的钳制规则未写。
3. **择吉排序依据未定义**：6.2 允许“展示排序”，但不输出总分；排序算法（命中数？优先级？权重和？）未定义，无法保证“同分按日期升序”的稳定性。
4. **禁用词“命中”与“规则命中”冲突**：9.1 禁用“命中”，但择吉/日志大量使用“规则命中”；扫描器需要上下文白名单，否则误杀。
5. **IL3 模板全集待冻结**（IF-01～IF-10），阶段 0 至少需要 IF-07 禁用词表与 IF-09 审核责任人。

### 2.4 CAL v0.1

**优点**

- 接口清单、输出对象、错误码、性能与缓存、逐日基准要求完整。
- 年柱立春切换、月柱节气切换、五虎遁/五鼠遁、旬空公式可直接实现。
- 日界、IANA 时区、夏令时重复/缺失处理均有明确条款。
- `LUNAR-MONTH-INDEX` 与 `JIEQI-MONTH-BRANCH` 强制分离，避免旺衰/纳甲误用农历月。
- CF-01～CF-10 待冻结项清晰。

**缺口 / 示例错误**

1. **1.2 输出示例数据不一致**（已复算）：
   - 示例称 `2026-11-03` 为农历 `2026-09-15`、日柱 `辛卯`、旬空 `甲申/午未`。
   - 实际 `2026-11-03` 为农历 `2026-09-25`、日柱 `辛巳`、旬空应为 `甲戌/申酉`。
   - `辛卯` 与 `甲申/午未` 内部自洽，但不对应 2026-11-03；该示例混用了不同日期的数据。
2. **8.1 基准数据示例农历年错误**：`2026-02-04` 在 2026 年春节（2026-02-17）之前，农历年应为 **2025**，示例写 2026。
3. **8.1 要求“2026 年逐日 + 闰月整月”，但 2026 年无闰月**（2025 闰六月、2028 闰五月）。基准年必须扩展或改为“任选含闰月的年份”。
4. **6.4 夏令时“向前平移”方向歧义**：中文“向前”可理解为更早或更晚；应明确 `02:30 → 03:30` 还是 `02:30 → 01:30`。
5. **6.2 `effective_date` 伪代码冗余**：`elif day_bound == ZIZHENG and hour >= 0` 恒真；建议改写为清晰分支，并明确 00:00–22:59 的 `ZICHU` 行为。
6. **5.3 日柱基准仍为候选**：1900-01-31 甲辰、2000-01-01 戊午、JDN 三条候选未冻结；阶段 0 必须选定并逐日校验。
7. **3.2 节气误差 ±60 秒待冻结**：需选定天文算法或预计算表，并记录 `CAL_EPHEMERIS`。

> 复算说明：以上日期/干支使用 `sxtwl` 与 `lunardate` 交叉核验；正式基准仍须以权威历书/天文台数据为准。

### 2.5 TDS v0.1

**优点**

- 技术栈、分层架构、模块边界、接口契约、SQLite 表、资源目录、隐私/加密、种子实现、日志、异常、部署、测试、迁移全覆盖。
- 模块边界表明确“谁不负责什么”，可直接指导代码结构。
- 隐私实现有 `BaziMaterial` 不序列化、HMAC 密钥进 Keychain、删除语义等具体条款。
- ADR 清单已列 10 项，便于阶段 0 决策。

**缺口**

1. **`bazi_material` 出现在 JSON 输入契约中**（3.4）：与“不序列化、不落盘”冲突，跨进程/IPC 时存在被日志或调试工具捕获的风险。
2. **`key_id` 缺失**：5.2 要求旧记录保留 `key_id` 验证，但 4.2 `runs` 表没有该列。
3. **资源目录含空格**：4.3 `texts/tui bei tu/` 建议改为 `tuibeitu/`。
4. **技术栈未冻结**：TF-01/TF-02/TF-05 均待原型验证；在冻结前不应把实现细节写成不可回退的契约。
5. **性能基准设备缺失**：TF-09 未定，SRS 6.2 的 P95 无法验收。

## 6. 结论与建议

1. **文档质量足以进入阶段 0**，但必须先修 9 项 P0 问题，尤其是 A-02（版本号）、A-03（A/B 种子）、A-04（Q/B 材料）、A-05（数据字典）、A-06（CAL 示例）、A-15（忌神算法）。
2. **不要先写 UI**。阶段 0 的正确顺序是：决策冻结 → 数据字典 → CAL 内核 → 种子/隐私 → 规则加载 → 梅花内核 → 金标准。
3. **不要先补 4096 条焦氏数据**。先用 `PENDING` 占位和完整性测试锁结构，数据校勘可与阶段 2 并行。
4. **把“待冻结项”变成可追踪的决策记录**，而不是留在文档表格里；否则每次讨论都会回到原点。
5. **SRS 升 v0.5 是阶段 0 的第一个交付物**，用于同步 TDS 状态、版本号、数据字典、种子字段与性能矩阵。
