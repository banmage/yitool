# 易学学习与推演记录工具 项目章程

## Core Principles

### I. 文档单一事实源与分层治理

SRS 定义“做什么、行为边界、验收”；ARS 定义“如何计算、映射、金标准”；IR 定义“计算结果如何转成文字解释”；CAL 定义“历法基础服务”；TDS 定义“如何实现”。任一模块 MUST 只在其职责范围内定义规则。

- 任何实现与 ARS/IR/CAL 冲突时，以 ARS/IR/CAL 为准，并回退修订 TDS。
- 任何行为与验收冲突时，以 SRS 为准。
- TDS MUST NOT 重新定义易学算法或解释模板；ARS MUST NOT 输出最终解释；IR MUST NOT 重新计算卦象；ARS MUST NOT 自行实现历法换算。
- 规则与程序分离：规则表、映射表、权重表、解释模板、古籍文本 MUST 以版本化配置/数据资源加载，不得散落硬编码。

**Rationale：** 五份文档是长期维护与历史复现的唯一依据，职责交叉会导致同一规则出现多个“事实版本”。

### II. 规则分层与典籍溯源（NON-NEGOTIABLE）

每一条规则 MUST 具备唯一 `rule_id`、规则层级、来源引用、版本、适用范围与测试样例。

- 层级固定为 `L1`（典籍原文/传统通行规则）、`L2`（本系统工程化解释）、`L3`（本系统自定义类象/权重/扰动）、`PROVISIONAL`（待校核）。
- `L3` MUST 显著标注“本系统自定义，非唯一流派”，MUST NOT 伪装为 `L1` 典籍原文。
- 每条步骤日志 MUST 记录 `rule_ids[]`、`data_refs[]`、`source_ref`、`rule_level`。
- 数据缺失或未校核时 MUST 显示“待校勘/待冻结/规则待校核”，MUST NOT 静默编造或回退近似值。

**Rationale：** 易学流派差异大，可追溯性是把“文化学习工具”与“伪权威预测”区分开的底线。

### III. 确定性与可复现

固定模式（`FIXED`）在相同规范化输入、相同规则/数据/算法/历法版本下 MUST 得到逐项相同的结果。

- 种子链 MUST 为 `基础种子 → 抽卡子种子 → 输入快照 → 推演种子 → 子种子`，且无循环依赖。
- 基础种子 MUST NOT 包含尚未产生的抽卡结果。
- 摇卦模式（`CAST`）MUST 保存原始随机快照与摘要；只承诺“凭快照可复现”，MUST NOT 宣称仅凭参数可复现。
- A/B 统一条件对照 MUST 共用基础种子、抽卡子种子与随机快照；问事文本差异 MUST NOT 改变共同随机条件。
- 每次推演 MUST 记录全部版本信息（SRS/ARS/IR/CAL/RULE/DATA/SEED/RNG/TZDATA）。

**Rationale：** 可复现是复盘、测试与隐私边界成立的前提；循环种子或未记录版本会直接破坏历史可信度。

### IV. 隐私最小化与不落盘（NON-NEGOTIABLE）

生辰八字与问事文本是最高敏感数据，系统 MUST 采用最小化处理。

- 生辰仅在当前推演会话内存中存在；MUST NOT 写入持久化存储、日志、导出快照或随机快照，MUST NOT 保存派生值，MUST NOT 参与可长期复现的推演种子。
- 问事文本默认不持久化；如需关联历史，MUST 使用本地密钥 HMAC-SHA256，不得使用裸 SHA256 作为可持久化匿名标识；原文保存 MUST 经用户显式确认并本地加密。
- 本地 HMAC 密钥 MUST 存放于 OS Keychain/Secret Service，不得写入数据库或日志；轮换不得重算旧记录。
- 应用内删除的语义 MUST 明确：不控制用户自行导出的文件与操作系统级备份。
- 每个涉及隐私的版本 MUST 提供“生辰不落盘”自动化扫描测试。

**Rationale：** 本地运行不等于零风险；一旦生辰或问事原文进入日志/备份，删除承诺即失效。

### V. 平行对照，不合成吉凶总分

梅花易数、焦氏易林、纳甲六爻 MUST 按各自规则独立运算、平行展示。

- 三引擎结果 MUST NOT 相加、加权平均或映射为统一“综合吉凶分数”。
- 引擎之间 MUST NOT 串用输入；九色/生肖 MUST NOT 作为纳甲起卦依据。
- 冲突 MUST 保留并解释来源（规则体系、输入、随机快照、数据待校核、模板差异），MUST NOT 静默覆盖。
- 焦氏易林只提供古典参考视角，不参与趋势打分。
- IR 可输出“综合观察建议”，但 MUST 标注为展示层建议，等级取最保守值，且不得表述为易学结论。

**Rationale：** 三套体系本就不可通约；合成总分会产生虚假确定性，违反项目合规定位。

### VI. 合规措辞与内容分区（NON-NEGOTIABLE）

所有输出 MUST 附免责声明，并遵守禁用措辞清单。

- 禁止“必然、一定、注定、命中、必死、必败、大凶、必成、包治、改命、化解灾祸、保证发财、绝对禁忌、必须避开”等绝对断语。
- 严格区分科学生活提醒、文化易学推演、情绪治愈内容，三类内容 MUST NOT 混排为同一结论。
- IR 措辞等级固定为 `偏顺/中性/需谨慎/信息不足/建议观察`，且受合规扫描约束。
- 幸运数与治愈文案 MUST NOT 与正式推演结果绑定，MUST NOT 包装为预测功能。
- 所有 IL3 模板与文案池 MUST 经安全审核并版本化。

**Rationale：** 合规文案是产品边界的最后一道闸门；任何绝对断语都会把学习工具变成误导性决策依据。

### VII. 版本化与历史只读复现

规则、数据、算法、历法、解释、数据库 schema MUST 独立版本化；历史记录 MUST 按生成时的版本渲染。

- 版本升级 MUST NOT 静默重算或改写历史记录。
- 旧七色记录 MUST 只读兼容，保留原 `COLOR-NUM-01` 规则版本，不用于新推演。
- 数据表与资源文件 MUST 带版本、校验和、来源与状态；加载时 MUST 校验 checksum。
- 旧版本资源可保留多个版本；资源缺失时 MUST 显示“原版本资源不可用”，不得静默替换。
- 导出快照 MUST 含完整性摘要，并默认脱敏。

**Rationale：** 易学规则会持续校勘；若历史随版本漂移，复盘与学习对照将失去意义。

### VIII. 金标准与测试先行

任何引擎在对应规则/数据冻结前 MUST NOT 发布正式结果；实现 MUST 以金标准测试为入口。

- 阶段 0 MUST 建立金标准测试框架，并覆盖：种子链、CAL 逐日基准、梅花九色与传统数字、旬空、隐私扫描、随机分布。
- 纳甲 MUST 使用多卦金标准（至少乾、坤、既济、未济、泰、否、同人、家人），MUST NOT 只用乾为天。
- 焦氏 MUST 覆盖 4096 键完整性；缺失条目 MUST 显式 `PENDING`。
- 性能指标 MUST 连同测试环境（设备、OS、数据规模、样本量、是否含初始化）一起记录。
- 未冻结项 MUST 在界面与日志标注“待校核”，并阻断“正式结果”文案。

**Rationale：** 易学规则无法靠主观“看起来对”验收；金标准是唯一可重复的质量证据。

### IX. 离线优先与本地轻量

核心功能 MUST 在无网络环境下完成；系统 MUST NOT 采集、上传个人数据或包含遥测。

- 默认本地单实例、多家庭成员轻量档案；档案之间历史、设置、偏好隔离，生辰不跨档案共享。
- 存储 MUST 使用本地单文件数据库（推荐 SQLite WAL），备份/恢复/迁移 MUST 可操作。
- 天气等联网能力仅为可选扩展，离线时 MUST 降级且不影响核心推演。
- 技术栈 MUST 支持 Windows/macOS/Linux 主流桌面环境，安装简单、体量可控。

**Rationale：** 自用、离线、轻量是项目的使用性质与隐私承诺的基础。

## Additional Constraints

- **技术栈基线：** TDS v0.1 推荐 Tauri 2.x + React + TypeScript + Vite + Rust + SQLite（WAL）；最终选型以阶段 0 原型验证与 ADR 为准。任何偏离 MUST 记录 ADR 并说明对接口契约的影响。
- **支持范围：** 默认公历 `1900-01-31` 至 `2100-12-31`；超出 MUST 返回 `CAL_OUT_OF_RANGE`，不得静默截断。
- **时间约定：** 所有历法接口 MUST 显式传入 IANA 时区与 `day_bound`；默认 `ZICHU`（23:00 换日），可配置 `ZIZHENG`。
- **性能基线（SRS 6.2）：** 种子生成 P95 < 50ms；单引擎推演 P95 < 200ms；三引擎平行 P95 < 500ms；一年吉日筛选 P95 < 500ms；1000 条内历史查询 P95 < 1s。
- **可访问性：** 抽卡、长按幸运数、展开日志 MUST 可键盘完成；颜色标识 MUST 色盲友好；动画 MUST 可关闭。
- **语言：** 界面与文案以简体中文为主；专业术语 MUST 提供悬浮释义。

## Development Workflow & Quality Gates

1. **Spec-Driven 流程：** `constitution → specify → clarify（按需）→ plan → tasks → analyze（按需）→ implement`。每次只创建一个特性规格，存放于 `specs/NNN-<short-name>/`。
2. **规格质量门：** `spec.md` MUST 通过 `checklists/requirements.md`；存在 `[NEEDS CLARIFICATION]` 时不得进入实现。
3. **阶段门（Phase Gate）：** 阶段 0–5 按 SRS 9.1 推进，不得跳阶。进入阶段 0 前/中 MUST 关闭 SRS 9.2 冻结清单；阶段 1 仅交付梅花单引擎闭环，不得宣称三引擎平行。
4. **实现门：** 先有金标准样例与失败测试，再有实现；禁止用实现输出反填金标准。
5. **评审门：** 每个特性合并前 MUST 通过：单元/金标准测试、隐私扫描、禁用措辞扫描、资源 checksum 校验、版本字段完整性检查。
6. **文档同步：** 规则/数据/接口变更 MUST 同步更新 SRS/ARS/IR/CAL/TDS 中对应条目并升版本；冲突 MUST 记录在案，不得口头裁决。
7. **决策记录：** 开放问题（O-xx）、待冻结项（F/CF/IF/TF-xx）关闭时 MUST 形成 ADR 或冻结记录，包含结论、依据、影响范围与生效版本。
8. **提交约定：** 使用 `docs:`、`spec:`、`feat:`、`fix:`、`test:`、`chore:` 前缀；一个提交只做一件事。

## Governance

- 本章程是项目最高治理文件；与其它文档冲突时以本章程为准，并回退修订下游文档。
- 修订章程 MUST 提交变更说明、版本号与迁移影响；版本遵循语义化：MAJOR（原则删除/重定义）、MINOR（新增原则/章节）、PATCH（措辞澄清）。
- 所有规格、计划、任务与代码评审 MUST 验证本章程合规性；复杂度或例外 MUST 在计划中说明理由与回退方案。
- 项目所有者为最终批准人；涉及隐私、合规、算法层级的变更 MUST 经联合评审（SRS/ARS/IR/CAL/TDS 责任人）确认。
- 运行时开发指引见 `AGENTS.md`；文档索引与项目状态见 `README.md` 与 `docs/00-PROJECT-ROADMAP.md`。
